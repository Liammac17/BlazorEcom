# Codebase review before the .NET 10 migration

Review date: November 6, 2026. Source baseline: commit `770f53f`.

## Coverage and method

The complete application was reviewed before choosing migration changes. Reviewers read every application source, project, solution, configuration, Razor, JavaScript, CSS, license, and documentation file in the baseline. The review also covered bundled source-map contents, binary asset metadata, and generated/local-file inventory.

The baseline contains **129 tracked files**: 127 application/solution/asset files and the two Git configuration files. The appendix lists every file to make the scope auditable. There were no application source tests, database creation scripts, migration scripts, CI workflows, Dockerfiles, or `global.json` in the starting source.

Binary assets were inspected as assets rather than treated as source code:

- The four Razor library background PNGs are small template stripe images; the three portal/common copies were confirmed identical 45×45 assets, and a representative image was viewed.
- The host favicon and Open Iconic font files were identified and inspected by format/metadata.
- Open Iconic's SVG font contains 223 glyphs. Its CSS, documentation, and font/icon license files were reviewed.
- The host's 13 static files include Bootstrap 4.3.1 CSS and its source map, Open Iconic 1.1.1 assets, site styling, and favicon. The Bootstrap map was parsed, including its 78 embedded sources, rather than reviewed only as an opaque minified line.

Existing `bin`/`obj` output was inventoried separately from maintained application files. The pre-migration generated-file review covered 164 artifacts: 55 cache files, 54 generated C# files, 11 editor configurations, 22 JSON restore/build records, 11 generated props, and 11 generated targets. These files describe previous builds and are regenerated by restore/build; they were not migration inputs or committed source.

The six existing `.vs` files were also inventoried. IIS Express's `applicationhost.config` was parsed, and design-time cache/SUO files were inspected through metadata and available binary headers. A Visual Studio file index under `.vs/eShop.Web/FileContentIndex/*.vsidx` was locked by the IDE; only its metadata could be inspected. This is the explicit review exception. Its application source inputs were reviewed directly, and the index is excluded from Git.

The review is a migration and behavior review, not a claim that the original store is ready for production or that all external systems were tested.

## Findings and migration decisions by area

| Area | What was reviewed | Finding and resulting migration decision |
| --- | --- | --- |
| Solution and projects | All 11 project files, references, SDKs, content/publish rules, solution configurations | Two executables target .NET Core 3.1; nine libraries target .NET Standard 2.0. Retarget all 11 to .NET 10 while preserving file locations, references, and SDK roles. |
| Host startup and routing | `Program`, `Startup`, `App.razor`, host/error pages, imports, layouts, navigation, launch settings | Traditional Blazor Server hosting can remain. Keep `UseStartup`, `AddServerSideBlazor`, `MapBlazorHub`, fallback hosting, prerendering, and existing routes. |
| Authentication | Cookie registration, controller, login view model/control, authorization components and attributes | The existing demo cookie flow is compatible with the retained host. Preserve behavior and document its existing limitations. |
| Core business | Product/order/line-item models, order service and interface | No framework-specific code changes required. Keep validation rules, model shapes, `double` prices, and nullable IDs/dates. |
| Use cases and interfaces | Every customer/admin use case and all data-store/cart/state interfaces | Existing repository/use-case boundaries remain compatible. Preserve signatures and implementations. |
| SQL repositories | Product/order SQL, Dapper helper and interface | Retain parameterized SQL, synchronous Dapper calls, and connection-per-operation pattern. Upgrade Dapper and move to `Microsoft.Data.SqlClient`; account for certificate validation in local development. |
| In-memory plugin | Both hardcoded repositories and sample product catalog | Compatible with .NET 10. Preserve the optional plugin and its existing behavior; production DI continues to select SQL repositories. |
| Local-storage cart and state | JSON serialization, JS interop, cart operations, state listeners, assets | Retain Newtonsoft.Json, the storage key and JSON model, interfaces, event contracts, and scoped state lifetime. Upgrade Newtonsoft.Json and the framework references. |
| Customer portal | All browsing/cart/checkout/confirmation pages, controls, view model, imports and assets | Keep components, markup, routes, and lifecycle patterns. Update the sole AutoMapper construction for the new logger-factory argument. |
| Admin portal | All outstanding/processed/detail pages, controls, imports and assets | No component logic changes needed for migration. Retain authorization and processing flow. |
| Common library | Login/message/search components, navigation helper/JS, view model and assets | No logic or asset changes required for migration. Replace old component packages with the shared framework reference. |
| Seed utility | Connection string, full sample product list and insert operation | Retarget and update the local SQL certificate settings. Preserve seed content and insertion logic. |
| Static/vendor assets | All CSS, embedded Bootstrap source-map sources, JavaScript, PNGs, favicon, fonts, SVG, licenses and vendor documentation | Assets have no .NET target dependency. Preserve the exact frontend design and bundled files. |
| Local/generated files | Restore/build artifacts and Visual Studio configuration, caches, index and settings | Keep output out of source control; add IDE and validation-output exclusions. Locked index exception is recorded above. |

## Existing limitations preserved

These findings existed before migration. They are recorded separately from framework compatibility changes so the migration remains faithful to the requested structure and patterns.

### Setup and persistence

- Database schema scripts are absent. SQL repositories require compatible `Product`, `[Order]`, and `OrderLineItem` tables in an existing database.
- Only the Development settings contain a connection string. Production must supply `ConnectionStrings__Default`.
- SQL order and line-item writes use separate connections without a transaction; partial persistence is possible on an intervening failure.
- Repository `QuerySingle` calls throw when a requested row is missing or non-unique.
- The seed utility has a hardcoded local connection, no table creation, no duplicate protection, and an insert without a column list. Several original product descriptions contain accidental `ProductId` text substitutions.
- The in-memory plugin's order dictionary is per repository instance. Its alternative singleton DI registrations remain commented out in `Startup`.

### Authentication

- `AuthenticateController` validates a hardcoded demonstration administrator account.
- Login credentials are sent to a GET endpoint in the query string; the login component interpolates values without URL encoding.
- Cookie authentication and page authorization are retained as originally implemented. The migration does not introduce a user store, role model, or production identity system.
- The login password field's visible label reads “Address.”

### Async, state, and error handling

- `AddProductToCartUseCase.Execute` is `async void`, and UI event/state handlers also use `async void` or discard `EventCallback` tasks. Navigation and error observation can race asynchronous cart work.
- `ShoppingCartComponent` adds a state listener without removing it on disposal; `CartComponent` does remove its listener.
- The local-storage cart assumes valid JSON, a non-null order/line-item list, and resolvable product references. Corrupt or stale browser data is not handled.
- Product/detail/summary components assume the referenced products and line items exist; invalid product IDs can cause an exception.
- The demo `FetchData` page injects `WeatherForecastService`, which is not registered in `Startup`.
- `ShoppingCart.PlaceOrderAsync` and the hardcoded order repository's `GetLineItemsByOrderId` throw `NotImplementedException`; the main SQL-backed checkout uses a different implemented path.

### Business and display behavior

- `OrderService.ValidateUpdateOrder` rejects a line item when `item.OrderId == order.OrderId`; this appears inconsistent with the usual ownership check and remains unchanged.
- Catalog rendering omits every sixth product because of the existing `i % 6 != 0` condition.
- Prices use `double`. The summary counts distinct lines, multiplies the stored line price by quantity, and displays zero shipping/tax.
- Confirmation and administration detail displays use current product prices, while the summary uses stored line-item prices.
- Product imagery is fetched from the existing external URLs.
- Bundled Bootstrap 4.3.1 and Open Iconic 1.1.1 are preserved. A NuGet dependency audit does not audit these static frontend assets.

## Validation boundary

The full file review informed a minimal framework/dependency migration. Build, publish, dependency audit, runtime, browser, and database results are tracked separately in [NET10-MIGRATION.md](NET10-MIGRATION.md). Reading an implementation does not establish that its external SQL Server or all business workflows were successfully exercised.
